# Патч QR-портала мерчендайзинга

`merch-portal-mount.patch` — минимальные изменения исходников отдельного портала на сервере мерчендайзинга, **не** копия его приложения. Исходники `/opt/pharmacy-crm-demo` на момент аудита 2026-09-23 не были Git-репозиторием. Патч подготовлен и проверен на изолированной копии; production-сервер им не менялся.

`strip-demo-autofill.mjs` — отдельный fail-closed sanitizer для исходного `src/Auth.jsx` с проверкой SHA-256. Он извлекает демонстрационные credentials **только в память**, удаляет автоподстановку без помещения старых строк в Git diff, собирает приложение и проверяет, что исходные значения отсутствуют в новых JS assets. Это лишь устранение публикации credentials: существующие активные учётные записи нужно отдельно отозвать/сменить на сервере. Не публиковать старые diff, бандлы и их резервные копии как публичные артефакты.

## Что исправляет

- Один Vite build загружает CSS/JS как с прямого `/staff`, так и с опубликованного ePharm `/merch/staff`.
- QR-страница `/merch/staff` открывает именно публичный портал заданий и отправляет запросы в `/merch/api/...`; прямой dev URL продолжает использовать `/api/...`.
- Фотоотчёты и эталон `/pharmacy-shelf.png` загружаются через соответствующий `/merch/` префикс. Переход к другому заданию сохраняет этот префикс.
- Восстановлен отсутствующий `src/catalogCities.js`: текущий исходный `PlacementPlanWorkspace.jsx` импортирует его, без него `npm run build` падает. Реализация перенесена из уже обслуживаемого на сервере JS-бандла `index-CuCqW6Jl.js` (SHA-256 `96bf8409e18298a65d1cb98bc26c72c89414f97fee9b3a4983289049bfdd5aed`), а не заменена заглушкой. Тест фиксирует набор из десяти значений «город требует уточнения» и алиасы Усть-Каменогорска.

Если хотя бы один SHA отличается, перепроверить diff; патч нельзя накатывать вслепую. Сначала нужен независимый backup исходников и `dist` на merch-сервере. В **отдельной staging-копии**, не в `/opt/pharmacy-crm-demo`, порядок такой: `git apply --check` → применение patch → перенос включённого lockfile в корень копии → `npm ci` → sanitizer `--check` и `--apply-and-build` → Node-тесты и browser smoke. Только после всех gate — атомарная замена live `dist` с планом отката; `strip-demo-autofill.mjs` прямо запрещает запуск с live-root. Создание отдельного Git-репозитория для исходников мерча — отдельная задача; этот patch bundle не должен становиться заменой контроля версий.

Проверенные команды в изолированной копии: sanitizer `--check`, sanitizer `--apply-and-build`, `node --test scripts/test_catalog_cities_recovery.mjs scripts/test_public_merch_mount.mjs scripts/test_public_merch_build.mjs`; 6 из 6 тестов прошли. Sanitizer проверил 25 новых JS assets. Сборка даёт только предупреждения Vite о chunk size и одном смешанном импорте.

В исходной поставке нет lockfile (`package-lock.json` и аналогов), поэтому первоначальная сборка через `npm install` не была воспроизводимой. В bundle включён сгенерированный на изолированной копии `package-lock.json` (его нужно положить в корень merch source после применения patch). Пакет `vite` намеренно обновлён с `6.4.1` до `6.4.3`: прежний lock давал один HIGH advisory для Vite dev server, новый `npm audit --audit-level=low` — 0 уязвимостей. Это уязвимость инструмента разработки, а не доказанный путь эксплуатации уже собранного Python-served `dist`. На новом lock `npm ci`, `npm run build` и 6 тестов прошли.

## Зависимости для rollout

Сам по себе SPA-патч недостаточен. ePharm Caddy должен публиковать **только** `/merch/staff`, нужные `/merch/assets/*`, `/merch/pharmacy-shelf.png`, фото через `/merch/api/task-files/*` и необходимые `POST /merch/api/public/task-dispatch*`; остальные CRM/API маршруты следует закрыть. Ключ интеграции сейчас передаётся к merch через публичный HTTP 8080 — до полноценного rollout требуется переход на проверяемый HTTPS upstream и согласованная ротация ключа. Проверки QR нужно проводить через новый тестовый токен в браузере телефона по мобильной сети: HTML, JS/CSS, эталон, чтение задания, загрузка фото, отправка, истёкший токен. Не проводить mutating smoke-тесты с реальным production-заданием без согласования.
