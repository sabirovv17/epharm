# Диагностика кассового источника остатков

Один универсальный батник для аптек со Standard-N и запущенной `zkassa`. Источник определяется по настройкам этой кассы; адрес конкретной аптеки в коде не задан. В начале можно ввести название/адрес аптеки либо нажать Enter. Название в отчёте — метка пользователя, не подтверждённая связь с ID аптеки; оно не выбирает БД.

## Запуск на Windows-кассе

### Если пароль из кассовой INI тоже отклонён

Запустите **`cashier-connection-audit.bat`** на той же кассе с открытой `zkassa`; для доступа к сведениям процессов и TCP рекомендуется запуск от имени администратора. Введите только название/адрес аптеки. Пришлите созданный на рабочем столе **`epharm-stock-connection-audit-*.txt`**.

Этот отдельный батник **не подключается к БД, не запускает isql и не проверяет пароли**. Он собирает путь/версию загруженного клиента, существующие TCP-соединения кассы к адресам из её конфигурации, PID/версию службы Firebird, слушающие порты и три несекретных параметра `firebird.conf`. Из credential-полей INI собираются только имена ключей, без значений, длин или хешей. Дамп процесса, командные строки и заголовки окон не собираются. Отсутствие TCP может означать XNET либо отсутствие соединения в момент снимка; IP/порт не доказывают идентичность БД, а наличие `firebird.conf` не доказывает применённую конфигурацию. Это следующий этап установления источника, не попытка изменить пароль или создать пользователя.

### Чтение системных метаданных при действующих данных входа

Когда данные INI не принимаются, а администратор предоставил действующие данные Firebird, используйте **`cashier-stock-metadata-manual.bat`**. Этот вариант выбирает источник из работающей кассы, затем запрашивает `LOCAL`, логин и скрытый пароль. Значения логина/пароля из INI не используются. Ввод пароля не сохраняется в BAT или TXT. Запускается одна попытка с фиксированными SELECT системных метаданных и обязательной read-only транзакцией; это не включает периодический сбор. Пароль передают оператору по закрытому каналу и вводят на кассе, не в переписке/репозитории. Для постоянного сборщика нужна отдельная проверенная учётка только для чтения.

### Точная структура объектов остатков после успешной общей диагностики

Если общая диагностика завершилась, но достигла лимитов 400 полей / 200 сегментов индексов, используйте **`cashier-stock-schema.bat`**. Это самостоятельный файл с теми же проверками источника, ручным логином и скрытым паролем. В отчёте — `VERSION=7` и `METADATA_SCOPE=TARGETED_STOCK_SCHEMA`.

Читаются только системные метаданные шести фиксированных объектов: `WAREBASE`, `PARTS`, `VW_WAREBASE`, `VW_WAREBASE_KASSA`, `WAREBASEPARTS`, `WAREBASEFOLDERS`. Отчёт включает поля и типы, вычисляемые выражения, сегментные индексы с признаками уникальности и направления, constraints, определения и зависимости двух представлений. Expression-индексы без сегментов здесь не перечисляются. Количества метаданных сверяются с количеством выведенных строк; превышение лимитов, отсутствие исходного текста существующей логики или усечение определений не считается успехом. Для `TARGET_SCHEMA_COMPLETE=TRUE` нужны также найденные `WAREBASE` и `PARTS`. Остальные кандидаты могут отсутствовать в этой версии Standard-N; это видно по списку найденных объектов.

Товарные строки, чеки и количество остатков не читаются. Планы и товарные SELECT ещё не выполняются: следующий этап — проверка плана фиксированного запроса, затем чтение одной известной партии и сверка с кассой. Нельзя трактовать названия `QUANT`, `REALQUANT`, `BLOCK_QUANT` как подтверждённое доступное к продаже количество.

### Проверка плана и проба одного товара

После получения структуры используйте **`cashier-stock-probe.bat`** (версия 8). Кассовая программа остаётся открытой. Запуск:

1. Введите название аптеки, подтвердите источник словом `LOCAL`, введите действующий логин и скрытый пароль.
2. Введите **штрихкод производителя** одного товара, который можно найти на экране кассы (6–32 цифры, нули в начале сохраняются). Если известен ID партии, используйте `PART:123`. Другие варианты идентификатора отклоняются.
3. Сначала выполняется `PLANONLY`: строк товара в этом этапе нет. Запрос обращается только к физической `WAREBASE`. Для штрихкода задан индекс `WAREBASE_IDX2(BCODE_IZG)` и максимум пять партий; для ID — `PK_WAREBASE(PART_ID)` и одна партия. Никаких подстановок другого индекса, представлений, процедур, JOIN, сортировок или полного обхода нет. Неподходящий план останавливает пилот.
4. После `STOCK_PLAN_STATUS=VERIFIED` введите `READ`, чтобы выполнить одну такую выборку. Enter завершит работу с отчётом плана. В каждой стадии проверяются read-only режим и текущая схема. Проверка схемы на сервере завершает SQL-пакет ошибкой **до товарного SELECT**, если изменились тип таблицы, состав обычных полей или индекс. Между стадиями используется тот же проверенный IP, без повторного выбора сервера по DNS.
5. Пришлите TXT и количество с экрана кассы по этому товару/партии. Отчёт содержит исходные `SAMPLE_QUANT`, `SAMPLE_REALQUANT`, `SAMPLE_BLOCK_QUANT`, `SAMPLE_BLOCK_COUNT`, сроки, единицу и служебные признаки. Формула доступного к продаже количества не применяется. При пяти строках другие партии могут существовать; отсутствие совпадения не означает пустую аптеку. Полный снимок не создаётся и не загружается в API.

Каждому дочернему isql даётся 10 секунд; повторов после ошибки, широких запасных запросов и постоянного расписания нет. Для регулярного сборщика потребуется отдельная проверенная SELECT-учётка. Сначала нужно установить смысл исходных количеств, резервов, срока годности, единицы/части упаковки и исключений кассы. Ручной `SYSDBA` используется только в этом разовом пилоте и не сохраняется.

1. Скопируйте на кассу один выбранный BAT: `cashier-stock-diagnostics.bat` для данных активной INI, `cashier-stock-metadata-manual.bat` для ручного ввода либо `cashier-stock-schema.bat` для точного описания объектов остатков. Другие файлы не нужны.
2. Оставьте обычную программу кассы `zkassa` запущенной. Запустите батник; если доступ к пути процесса закрыт, повторите от имени администратора. Подсказки и запросы ввода в PowerShell — на русском.
3. Диагностика покажет адрес БД и сведения о конфигурации. При отсутствии однозначного источника, обнаружении известной центральной БД или отсутствии установленного Firebird `isql` запросы к БД пропускаются.
4. Если источник действительно относится к этой аптеке, введите `LOCAL`, чтобы разрешить разовое чтение **системных метаданных**. При сомнении нажмите Enter. Обычный вариант использует существующие данные подключения из однозначно выбранной активной `options.ini`; фиксированный логин `READONLY_USER` не подставляется. В ручном варианте логин/пароль вводит оператор.
5. Если полные однозначные данные подключения из INI отсутствуют, можно ввести действующий логин и скрытый пароль для чтения этой БД либо нажать Enter. После отказа сервера других попыток нет. Имя учётки и успешная диагностика не доказывают ограниченные права.
6. Пришлите текст между `EPHARM STOCK DIAGNOSTICS BEGIN` и `END` либо созданный `epharm-stock-diagnostics-*.txt` на рабочем столе. Окно остаётся открытым до нажатия клавиши.

Батник содержит весь PowerShell-код и SQL. Требуется установленный Windows PowerShell 5.1. Ничего не скачивается и не устанавливается на кассу. Скрипт не отправляет SQL записи и не меняет настройки, службы, расписания или POSM. Файлы FDB не копируются и не открываются встроенным движком. Отчёт и временный SQL — единственные записи скрипта в файловую систему; временный SQL удаляется при завершении. На сайте и `.81` ничего не меняется.

## Ограничения

- При поиске источников логин/пароль INI игнорируются. Только после `LOCAL` для разовой диагностики перечитывается единственная активная INI; изменение адреса или неоднозначность запрещают запрос. Логин и пароль передаются только дочернему процессу `isql` через `ISC_USER`/`ISC_PASSWORD`, не аргументами или SQL. Нет SYSDBA/default паролей и смешивания частичных конфигураций с ручным вводом. Отчёт маскирует пароль и поля секретов; секреты не сохраняются в файлах. Для постоянного сборщика требуется отдельная проверенная SELECT-only учётка.
- Блокируются известные центральные имена, адреса и групповые пути; это не универсальный способ доказать принадлежность любого неизвестного сервера аптеке. Поэтому необходимы проверка адреса оператором и подтверждение `LOCAL`. Нет переключения на запасную базу.
- Если `zkassa` не найдена, отчёт включает ограниченный список подходящих процессов (имя и путь исполняемого файла). Командные строки и заголовки окон не читаются. Этот список помогает установить другое имя кассовой программы; сам по себе он не разрешает подключение к БД. Конфигурация из известного каталога с `FROM_RUNNING_CASHIER=False` — только кандидат, а не подтверждённый рабочий источник.
- Выполняются один раз фиксированные SELECT из `RDB$...` в явно `READ ONLY` транзакции. Рабочие остатки, чеки, товары и персональные данные не читаются. Метаданные ограничены 120 именами объектов, 400 полями и 200 сегментами индексов; отсутствие поля в усечённом отчёте не доказывает его отсутствие в БД.
- Успех требует полного маркера окончания и `RDB$GET_CONTEXT('SYSTEM','READ_ONLY')=TRUE` (Firebird 2.5.3+), а не только кода выхода 0. SQLSTATE 28000 сам по себе не различает неправильный вход и нехватку прав: конкретная причина классифицируется по сообщению/GDS-коду. Серверные триггеры подключения могут иметь собственные действия; режим read-only нашего SQL не отключает их. Скрипт не меняет триггеры или права.
- `isql` получает 10 секунд на подключение и чтение; при превышении завершается только запущенный диагностикой дочерний процесс. Это клиентское ограничение, не доказательство мгновенной отмены серверного запроса. Автоматических повторов нет.
- Проверки разработчика выполняются на PowerShell вне кассы. Подтверждение совместимости с конкретной Windows/Firebird и установление схемы остатков — результат этого пилота. На этом этапе не включается периодический сбор.

Версия 6 исправляет ошибку совместимости SQL с Firebird 2.5: зарезервированный псевдоним `POSITION` заменён на `FIELD_ORDINAL` / `INDEX_FIELD_ORDINAL`. Оба пакета SQL проверены настоящим движком 2.5.9 на синтетических таблицах; результат чтения схемы конкретной аптеки должен подтвердить новый отчёт кассы.

Версия 7 добавляет точечное чтение структуры остатков с проверкой полноты. Его SQL также проходит проверку на Firebird 2.5.9; общее чтение и аудит подключения сохраняются как отдельные варианты запуска.

Версия 8 исправляет два ложных отклонения отчёта Windows: окончания строк CRLF и выражения представлений без индивидуального `COMPUTED_SOURCE`. Для выражения представления требуется полное `VIEW_SOURCE`; для вычисляемой колонки физической таблицы по-прежнему требуется её собственный источник. Присланный отчёт версии 7 от 14 октября, 19:24, повторно проверен локально и признан полным; заново собирать схему не требуется. Добавлен отдельный режим плана/пробы одного товара.

## Исходники и проверки

Редактируемый источник: `cashier-stock-diagnostics.ps1`. После правок пересоберите BAT:

```sh
python3 stock-service/pilot/build-diagnostics-bat.py
```

Проверка адресов, секретов, SQL и упаковки без подключения к Firebird:

```powershell
pwsh -NoProfile -File stock-service/pilot/test-diagnostics.ps1
pwsh -NoProfile -File stock-service/pilot/test-connection-audit.ps1
pwsh -NoProfile -File stock-service/pilot/test-stock-probe.ps1
```

Проверка всего SQL на Firebird 2.5.9 (нужны Python 3 и работающий Docker на машине разработчика):

```sh
python3 stock-service/pilot/test-firebird25-metadata.py
```

Проверка создаёт пустые временные БД и синтетические таблицы в контейнерах с `--network none`; порты, существующие тома и каталоги хоста не подключаются. Образ закреплён по digest. Данные входа исключительно тестовые. После проверки контейнеры и их анонимные тома удаляются. Проверяются исходная ошибка `POSITION`, выполнение трёх SQL-пакетов, вывод полей/индексов, версия движка, `READ ONLY`, полное завершение и совпадение контрольных количеств точечных метаданных. Запуск не обращается к аптечным БД и не проверяет схему или нагрузку рабочей кассы.

Полная проверка плана и sample на синтетической Firebird 2.5.9 (PowerShell 7, Python 3 и Docker):

```powershell
$probeTestDir = Join-Path ([IO.Path]::GetTempPath()) ('epharm-stock-probe-test-' + [Guid]::NewGuid().ToString('N'))
pwsh -NoProfile -File stock-service/pilot/test-stock-probe.ps1 -ExportSqlDirectory $probeTestDir
if ($LASTEXITCODE -ne 0) { throw 'PowerShell probe checks failed' }
python3 stock-service/pilot/test-firebird25-stock-probe.py $probeTestDir
if ($LASTEXITCODE -ne 0) { throw 'Firebird probe checks failed' }
pwsh -NoProfile -File stock-service/pilot/test-stock-probe.ps1 -NativeOutputDirectory $probeTestDir
if ($LASTEXITCODE -ne 0) { throw 'Native output checks failed' }
Remove-Item -LiteralPath $probeTestDir -Recurse -Force
```

Первый шаг экспортирует SQL из самого PowerShell-источника. Второй проверяет оба идентификатора и обе стадии: read-only, точный индексный план, отсутствие товарных строк в PLANONLY, только выбранные партии в sample. Дополнительная синтетическая проверка меняет обычное поле количества на вычисляемое и подтверждает отказ серверной проверки до чтения товара. Третий шаг применяет проверки батника к настоящему выводу Firebird. При любой ошибке остановите проверку и исправьте её до распространения BAT; реальные credentials здесь не используются.

Использование `ISC_PASSWORD` и batch-only `-bail` проверено по [переменным среды Firebird](https://www.firebirdsql.org/docs/chunk/en/refdocs/fbconf/fbconf-environment-variables.html) и [руководству isql](https://firebirdsql.org/file/documentation/html/en/firebirddocs/isql/firebird-isql.html).
