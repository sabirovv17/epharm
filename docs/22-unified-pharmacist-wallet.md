# Единый денежный баланс фармацевта

Деньги за рекомендации, обучение и подтверждённые задания мерчендайзинга учитываются
на существующем балансе ePharm `pharmacists.balance`, в целых тенге. Остатки товаров
из CRM — другой показатель: они не складываются с денежным балансом.

## Учёт и выплаты

`PharmacistWalletService` сериализует изменение баланса блокировкой строки фармацевта.
Первое изменение сохраняет текущий баланс как начальную контрольную точку, без
придуманной истории старых начислений. Новые движения записываются в неизменяемый
журнал `pharmacist_wallet_entries`; повтор того же источника не начисляет деньги снова.
Изменение получателя, суммы или контекста существующего движения вызывает конфликт.

Ключ бонуса за рекомендацию — ID `pending_bonus`, а не ID повторно загруженного чека.
Ключ обучения — ID назначения. Мерчендайзинг начисляется один раз на назначение CRM.
Ручная коррекция баланса также оставляет отдельное движение. Формирование выплат
резервирует текущий доступный баланс и записывает отрицательное движение. Это **не
подтверждение банковской выплаты**; автоматических переводов или возвратов здесь нет.
Конкурентные начисление и резервирование не должны терять деньги.

Существующая сверка рекомендаций не заменяет доказательство продажи показом или
автоматически сгенерированным принятием. У информационного POSM-окна нет действия
`accepted`: связать его фактический показ с проверенной продажей и резервом бонуса —
отдельный поток с отдельными проверками. Простое включение денежного журнала этот
продуктовый разрыв не закрывает.

## Вознаграждение за задание CRM

Безопасный default — `MERCH_REWARDS_ENABLED=false`. В таком состоянии новый денежный
поток недоступен, существующие рекомендации, вход и задания продолжают работать.
Для включения нужен отдельный общий секрет `PHARMAPAY_REWARDS_SHARED_SECRET` не короче
32 байт и реальный OTP-провайдер с `OTP_DEV_MODE=false`. QR integration key и JWT secret
для этого не используются. Секреты не добавляются в Git, URL, журнал или документацию.

Последовательность:

1. CRM выдаёт подписанный контекст конкретного назначения и аптеки, суммы и срока.
2. Сотрудник открывает `/learn/merch/claim#challenge=…`, входит в ePharm и подтверждает
   **свежий отдельный OTP**, отправленный только на телефон его активного профиля.
   Сам вход по паролю и произвольное имя исполнителя не являются подтверждением.
3. ePharm выдаёт непрозрачный grant на 120 секунд. В базе хранится только его хеш.
   Возврат идёт строго на `https://crm.inkar.kz/staff` через fragment, без JWT.
4. CRM подписанным серверным запросом обменивает grant на неизменяемую связь с реальным
   фармацевтом. Аптека должна точно совпадать с профилем; другой человек не может
   перепривязать уже назначенное вознаграждение.
5. Только после выполнения задания этим исполнителем и одобрения менеджером CRM
   отправляет неизменяемое событие начисления. Открытие QR, получение grant или отправка
   фото сами по себе деньги не начисляют.

Старые задания задним числом не начисляются. Сумма фиксируется в подписанном контексте
и связи исполнителя; изменение суммы требует отдельного согласованного процесса,
а не изменения уже выпущенного события. Заблокированный или переведённый в другую
аптеку сотрудник не получает новое начисление автоматически: событие остаётся для
разбора, без догадок о новом получателе.

Срок задания ограничивает **выполнение и отправку отчёта**, не последующее рассмотрение.
Подписанное событие содержит серверный `submittedAt`: он должен быть после привязки
исполнителя, не позже `taskDueAt` и не позже одобрения. Позднее рассмотрение и повторная
доставка своевременно выполненного задания разрешены. Синхронизация времени ePharm,
CRM и БД — обязательная эксплуатационная предпосылка; просрочка не продлевается автоматически.

## API и подписи

Все мобильные маршруты требуют pharmacist JWT и повторно проверяют активность и аптеку
в БД. Ответы помечены `Cache-Control: no-store`.

| Маршрут POST | Назначение |
| --- | --- |
| `/api/mobile/merch/executor-grants/context` | `{crmChallenge}` → доверенные название, аптека, сумма KZT, срок и маскированный телефон |
| `/api/mobile/merch/executor-grants/otp/request` | `{crmChallenge}` → ID отдельного OTP, маска телефона, срок, cooldown |
| `/api/mobile/merch/executor-grants` | `{crmChallenge, otpChallengeId, code}` → grant, срок и фиксированный redirectUrl |
| `/api/integrations/merch/executor-grants/redeem` | подписанные `{grant, dispatchId, pharmacyId, nonce}` → bindingId и фактический pharmacistId |
| `/api/integrations/merch/reward-events` | подписанное одобрение → `{eventId, credited:true, duplicate}`; 201 новое, 200 точный повтор |

Контекст: `v1.payloadBase64url.signatureBase64url`, без padding. HMAC-SHA256 подписывает
UTF-8 строку `epharm.merch.claim.v1\n` + исходный payloadBase64url, без пересериализации JSON.
Поля: `iss=crm.inkar.kz`, `aud=epharm`, `dispatchId` UUID, `pharmacyId`, случайный `nonce`
32 байта, `iat`, `exp` Unix seconds (TTL ≤600 секунд), `taskDueAt` Unix seconds,
`taskTitle` ≤160 символов и положительная целая `rewardKzt`. `exp` не позже срока задания.

Серверные POST используют `X-Merch-Timestamp` (Unix seconds) и `X-Merch-Signature`
(hex HMAC-SHA256) над строкой с разделителями `\n`:

`epharm.merch.request.v1`, timestamp, HTTP method, exact path + query, SHA-256 hex сырых bytes тела.

Допустимый дрейф подписи — 300 секунд; тело ограничено 16 KiB. Повторная доставка
подписывает новый timestamp, но сохраняет eventId и исходные bytes. Событие содержит
`schemaVersion=1`, `type=merch_task_approved`, `eventId`, `dispatchId`, `bindingId`,
`pharmacyId`, `amountKzt`, `currency=KZT`, `submittedAt`, `approvedAt`, `approvedByCrmUserId`.
Получатель определяется по сохранённой связи, не принимается из тела события.
Зачисление и запись одобрения коммитятся в одной транзакции. Дедупликация работает
и по ID события, и по назначению; изменённый повтор возвращает 409.

При включённом денежном потоке SMS для mobile/POSM/merch используют общий phone-wide
cooldown и взаимно инвалидируют OTP-подтверждения разных назначений. Код входа нельзя
использовать как код подтверждения задания. При выключенном флаге старое поведение
авторизации не меняется. В ответах денежного API нет `devCode`.

## Приёмка и откат

До включения обязательны: CI обеих сторон, межъязыковые векторы HMAC, тесты конкуренции
на PostgreSQL, проверка резервной копии и согласованный пилот с реальным телефоном,
одним исполнителем и одобрением менеджера. Локальные тесты используют mock OTP, не
отправляют настоящие SMS и не меняют production-деньги.

Отключение флага останавливает новые grants/начисления, но не удаляет баланс и журнал.
При откате backend нельзя удалять применённые миграции или редактировать историю.
Старый backend может читать расширенную схему, но не знает защиты новых денежных
писателей; при возврате к нему сначала остановить выдачу новых CRM rewards. Наличие
журнала намеренно запрещает удалять связанного фармацевта вместе с финансовой
историей. Последующие исправления — отдельные проверенные движения, не UPDATE журнала.
