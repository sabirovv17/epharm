# Проверки первого этапа: отчёты и план РПС

Это локальная проверка кода, не акт внедрения на всех кассах и не production-деплой.
Ветка `codex/rps-rollout-foundation`, исходная база `aef761c`. Исходное грязное
дерево пользователя сохранено. Редактор, RulesEngine, применённые миграции,
release guards, production-данные и контейнеры не изменялись.

## Что реализовано

- Отдельный backend `reporting`: read-only JSON/PDF по одной кампании, HQ/SYSTEM_ADMIN.
- Раздельные выдачи, фактические ACK-показы, принятия, подтверждённые продажи и
  подмножество 0–120 с. «Одобрено замен» — все подтверждённые продажи замен.
- Дедупликация чек/SKU, проверка связи аптеки/сессии/времени чека, границы Алматы.
- Конверсии по той же когорте показов; при нуле показов значение `null`, в PDF `—`.
- Форма `/dashboard/reports`, кнопка с дашборда, валидация дат, сохранение выбора
  при ошибке, запрет повторной выгрузки, отмена при уходе, MIME/error проверка.
- DEMO PDF с синтетическими данными, графиком, KPI, дневной таблицей и методикой.

Backend запуск:

```bash
cd admin-panel/backend
./gradlew test --tests 'kz.epharm.reporting.*' \
  --tests '*DashboardIntegrationTest' --tests '*RecommendationAttributionIntegrationTest'
```

Для генерации синтетического образца в тесте можно задать `REPORTING_DEMO_OUTPUT`
абсолютным путём к `.pdf`. Эта переменная не читает production и не меняет API.

Проверка админки:

```bash
cd admin-panel/frontend
npm run lint
NODE_OPTIONS=--no-experimental-webstorage npm test
VITE_API_BASE_URL= npm run build
npx playwright test --config playwright.artifact.config.ts
```

Первый полный Vitest-запуск в локальном Node 26 упал в 11 прежних learner-тестах:
его native `localStorage` был недоступен без файла. Повтор с отключённым Node
webstorage дал 514/514; код learner и тестовая настройка не менялись. CI закреплён
на Node 24.15.0. Это триаж среды, не игнорирование красной проверки.

Browser suite обслуживает `dist` через изолированный Vite preview, блокирует
внешние/неизвестные запросы, подставляет только синтетические аккаунты и API.
Новый download-тест проверяет транспорт mock PDF, не подменяет серверные PDF-тесты.
Проверка именно release Docker image, CI текущего PR и production smoke — отдельные
обязательные gates перед публикацией; здесь они не выполнялись.

## Что ещё не реализовано/не принято

Новый серверный вход/регистрация/сброс РПС, WPF-окно и независимый session watcher
пока имеют исследованный контракт, но не реализованы этим изменением. Последнее
решение владельца: кассу и Windows **не блокировать**; vendor hook запрета продаж
не требуется. Не выдавать существующую атрибуцию продавца за новый подтверждённый вход.

Нужна единая проверка на изолированной Windows-кассе: скан → реальный popup → ACK
→ закрытый чек → тот же результат в PDF, плюс startup/switch/reset/offline. SQL
fixtures и portable C# tests сами по себе этого не доказывают. Финальные видео
записываются только после принятого реального интерфейса; сейчас есть сценарии.

Историческая принадлежность отчётных событий ограничена текущей связью
`rules.promo_id`; она явно отражена в PDF. Реальные суммы выручки/выплат не считаются.
Существующий pipeline подтверждает состав чека до атрибуции; отчёт не делает новый
неоднозначный матчинг сырых названий. Перед production нужен performance smoke на
репрезентативном обезличенном объёме, не только небольшие тестовые fixtures.

Текущие кампании в админке тестовые и сохраняются. Актуальных программ Инкар для
импорта нет по сообщению владельца; новые программы/активации/финансовые изменения
и приглашение на финальный созвон не выполнялись.
