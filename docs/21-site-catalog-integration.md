# Каталог «Аптека со склада» в Epharm

Этот контракт описывает замену источника каталога и цен для админки, мобильного
приложения и акций. Правила POSM используют локальную таблицу `products`; её
идентификаторы и проверенные кассовые ключи сохраняются.

## Источник и границы

На дату проверки 2026-10-10 живой сайт и его PostgreSQL работают на `.80`.
Публичный `aptekasosklada.kz` проходит через `.81`, но `.81` не является базой
каталога. Старый `inkeshopapteka.inkar.kz` возвращал 502 и не должен быть URL
импорта. Публичный `/api/catalog` отдаёт только опубликованный ассортимент и
использует меняющуюся доступность; обход offset-страниц не даёт согласованный
полный справочник.

`ops/eshop-catalog-exporter/` запускается отдельным процессом в Docker-сети
базы сайта. Он получает только `SELECT` к таблицам каталога, доступности и
проверенной таблице связей старых ID. HTTP слушает частный адрес `.80`, доступный
только backend Epharm на `.76`, и требует отдельный случайный Bearer-токен.
Сайт, Caddy и база магазина не перезапускаются при обновлении Epharm.

`GET /v1/snapshot` возвращает NDJSON в одной транзакции PostgreSQL
`REPEATABLE READ READ ONLY`. Первая строка фиксирует `catalogRunId`,
`availabilityRunId`, ожидаемое количество и время снимков. Далее товары идут по
SKU; каждая строка содержит исходный объект сайта, эффективную цену, флаг
`published` и только подтверждённые старые ID. Завершающая строка содержит
количество и SHA-256 всех строк товаров с LF. Клиент проверяет схему, размер,
уникальность SKU/ID/alias и SHA-256, а затем одной транзакцией публикует новое
поколение в PostgreSQL Epharm. Ошибка экспорта или проверки оставляет последнюю
полную версию доступной.

`published` отражает правило видимости сайта: у товара есть вариант и
положительная цена из каталога либо актуальной доступности. Админка видит весь
полный справочник (в том числе неопубликованные позиции с отсутствующей ценой),
мобильный каталог — только опубликованные товары с действующей товарной акцией.
«Действующая» означает статус `active`, дату внутри окна Asia/Almaty и корректные
положительные ступени цены/количества; истёкшая, черновая или некорректная акция
не открывает товар в мобильном каталоге. Публичные API Epharm сохраняют свои
контракты; клиентские приложения не соединяются с экспортёром. Изображения
проходят через `/api/media/eshop?sku=...`: сервер проверяет SKU и обращается
только к фиксированному HTTPS-origin сайта.

Снимок каталога сайта обновляется по расписанию самого сайта, а доступность —
отдельно. Epharm повторно забирает согласованное поколение; это **не** API
живых кассовых остатков. Возраст каждого снимка и последняя ошибка видны в
`/api/health`.

## Акции и POSM

Новые карточки получают ID сайта. Существующие акции и правила остаются на
старых ID, пока соответствие подтверждено таблицей связей; несколько старых ID
могут вести к одному SKU. Замена ID правил по названию запрещена. Если связи
нет, локальный `ProductEntity` и его правило остаются в базе, а POSM продолжает
использовать прежние barcode/iPartID/название/цену. Такое правило нельзя
автоматически переносить на новую карточку.

Источник Daribar сейчас не содержит нормализованных штрихкодов. Для нового
правила с точным товарным триггером администратор должен указать проверенный
barcode или iPartID кассы до активации. Наличие карточки в каталоге само по себе
не доказывает, что POSM сможет сопоставить товар в чеке. Текущие правила и
широкие ACC-триггеры сохраняют существующую логику.

## Переход и возврат

1. Выполнить резервное копирование Epharm и сайта `.80` и проверку
   восстановления обеих баз, затем
   развернуть read-only экспортёр на `.80` с ограничением сети и собственным
   токеном. Проверить его `/health` и один полный поток в тестовом окружении.
2. Развернуть backend с `ESHOP_CATALOG_SYNC_ENABLED=true`, оставив
   `ESHOP_CATALOG_ADMIN_READ_ENABLED=false` и `ESHOP_CATALOG_READ_ENABLED=false`.
   Дождаться полного поколения и проверить
   число всех и опубликованных товаров, ID связей, поиск, цены и изображения.
3. Проверить на тестовом контуре существующие акции и рекомендацию с
   несопоставленным старым ID. До мобильного переключения сверить каждую
   активную акцию с опубликованной карточкой сайта; несопоставленный товар не
   угадывать по названию. Сохранить его локальный товар и правило POSM.
4. Включить `ESHOP_CATALOG_ADMIN_READ_ENABLED=true` отдельной backend-only
   транзакцией. Проверить полный справочник и фильтр опубликованности в админке;
   мобильный каталог остаётся прежним. На этой промежуточной стадии новые акции
   с site ID можно готовить как черновики, но их активация блокируется до
   мобильного переключения. Проверить существующие акции и POSM.
5. На тестовом контуре подготовить проверочные товары: опубликованный с активной
   действующей акцией, опубликованный без акции и скрытый на сайте после
   активации акции. На production выбрать известную действующую опубликованную
   акцию для smoke. Включить
   `ESHOP_CATALOG_READ_ENABLED=true` отдельной транзакцией. Проверить, что
   мобильный список и карточка показывают только первый товар, админка видит все
   три, а рекомендации POSM и pop-up работают. Общий mobile count зависит от
   кампаний и не является фиксированным. При ошибке сначала откатить mobile,
   затем при необходимости admin; Flyway-миграции не откатываются.
6. С момента переключения обоих контуров новый backend не должен обращаться к Medusa,
   включая фоновые обновления цен. Предыдущий полный снимок и конфигурацию
   сохранить до завершения окна отката; после него удалить устаревшие доступы.
   Проверять фактическое отсутствие запросов по логам/метрикам, а не только по
   значению флага.

Секреты экспортёра и Epharm находятся только на серверах (mode 0600) и не
попадают в Git, отчёты или диагностические ответы API.
