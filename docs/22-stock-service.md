# Сервис остатков: эксплуатация и интеграция

## Что работает сейчас

Действующий API запущен на `10.10.1.81` и доступен внутри корпоративной сети по
`https://inkeshopapteka.inkar.kz/stocks/api/v1/`. Шлюз на `.80` пересылает
этот путь на Nginx `.81`, далее на контейнер `127.0.0.1:18080`. Остальные
маршруты сайта остаются на `.80`. Опрос групповой Firebird Standard-N **выключен**
`STOCK_COLLECTION_ENABLED=false`. До переключения на ветку PostgreSQL сервер
отдаёт исторический SQLite-снимок; все старые данные устарели. Возвращать
центральный обход нельзя: источник не отражает изменения кассы в реальном
времени и создаёт нагрузку на групповую базу.

Ветка `codex/stock-cashier-postgres` содержит замену хранилища на отдельный
PostgreSQL и серверный приём полных снимков от касс. Её запуск в production и
подключение кассового сборщика — отдельные проверяемые этапы. Факты о пилоте,
неизвестные поля локальной базы и критерии включения изложены в
[плане перехода](23-cashier-stock-transition.md).

## Контракт для потребителя

Машинный контракт: [`stock-service/openapi.yaml`](../stock-service/openapi.yaml).
Все маршруты `/stocks/api/v1/*` требуют
`Authorization: Bearer <STOCK_API_KEY>`. Ключ выдаёт администратор сервиса;
его нет в Git. Базовый URL и этот ключ сохраняются при замене хранилища, так
что клиенту со стабильным URL повторная привязка не нужна.

| Маршрут                                                | Смысл                                                                  |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| `GET /status`                                          | Счётчики `fresh/stale/pending/error`, режим сбора и последняя попытка. |
| `GET /cities`                                          | Города и число активных профилей.                                      |
| `GET /pharmacies?city=...`                             | Каталог и статус каждой аптеки.                                        |
| `GET /pharmacies/{id}`                                 | Одна аптека.                                                           |
| `GET /pharmacies/{id}/stocks?limit=100&offset=0&q=...` | Страница партий, `total`, `asOf`, `snapshotId`.                        |

Здесь маршруты указаны относительно `/stocks/api/v1`. Для последующих страниц
передавайте `snapshot=<snapshotId>` с первой страницы. При `409 snapshot_changed`
начните чтение заново. До первого полного снимка `stocks` отвечает `503`; только
успешный полный пустой снимок означает нулевой остаток. `quantity` — физическое
положительное количество по партии, **не подтверждённое доступное к продаже**.
`sourceKind=central_legacy` всегда исторический; `cashier_local` появляется
только после подтверждённого локального чтения. Для продажи и резерва нельзя
использовать `stale`, `error`, `pending` и `sellableVerified=false`. `profileId`
Standard-N необходимо явно сопоставлять с ID HQ, а партию идентифицировать
парой `profileId + sourceId`; `partId` повторяется.

Время `asOf` старого снимка сохраняется при миграции, поэтому перенос в новую
БД не улучшает свежесть. Для локального снимка отдельно выдаются
`sourceObservedAt` (завершение чтения кассы) и `ingestedAt` (приём сервером).
Цель обновления — три минуты на аптеку; гарантия для всей сети пока не
подтверждена измерениями локального источника. Читайте фактические статусы API.

## Код и изоляция

- [`stock-service/Program.cs`](../stock-service/Program.cs): HTTP-маршруты.
- [`stock-service/StockRepository.cs`](../stock-service/StockRepository.cs): транзакционная публикация полного снимка, запросы и индексы PostgreSQL.
- [`stock-service/CollectorAuth.cs`](../stock-service/CollectorAuth.cs): отдельный токен кассы, ограниченный одной аптекой.
- [`stock-service/stock-service-migrate/`](../stock-service/stock-service-migrate/): однократный импорт исторического SQLite; обслуживающий процесс SQLite не использует.
- [`stock-service/collector-openapi.yaml`](../stock-service/collector-openapi.yaml): внутренний контракт приёма от кассы. Шлюз этот путь пока не публикует.
- [`stock-service/compose.yml`](../stock-service/compose.yml): отдельный PostgreSQL 17 в закрытой Compose-сети, роль приложения без DDL, ограничения ресурсов и локальный порт API.

Рабочая копия на `.81`: `/home/adm-quasar/epharm-stock-code`;
живой исторический SQLite: `/home/adm-quasar/stock-service/data/stocks.sqlite`.
Файл `.env` хранится только на сервере с правами `0600`. PostgreSQL для сервиса
не должен разделять экземпляр с CMS/HQ. На `.81` под него следует выделить
отдельный том, а резервную копию вывозить с сервера. `/healthz` проверяет
процесс; `/readyz` и Docker healthcheck выполняют короткий запрос к PostgreSQL.
Ни одна из этих проверок не измеряет свежесть содержимого — для неё нужен
`/api/v1/status` и оповещение при росте `staleCount`/`errorCount`.

## Порядок переключения на PostgreSQL

1. Зафиксировать commit релиза, сохранить прежний Docker-образ и конфигурацию.
   Убедиться по `/status`, что центральный сбор выключен. Сделать согласованную
   копию SQLite через backup API или остановку контейнера; проверить
   `PRAGMA quick_check`. Сохранить её вне `.81`.
2. Выделить отдельный том для PostgreSQL, установить права каталога для UID
   контейнера и задать три независимых случайных пароля в `.env` по
   [образцу](../stock-service/.env.example). Проверить `docker compose config`
   без вывода переменных в лог.
3. Запустить `postgres` и одноразовый `stock-db-init`, затем `stock-migrate`
   с read-only монтированием **зафиксированной** копии SQLite. Импорт
   отказывается работать на непустой целевой БД и сверяет числа аптек/строк,
   активность, pending/error и границы `asOf`. Повторный запуск проверяет маркер.
4. Сделать `pg_dump -Fc` и проверить восстановление в отдельную БД. Настроить
   регулярные резервные копии вне `.81`, контроль успешности и места на диске.
   До этого не переключать потребителей.
5. Запустить новый API на локальном тестовом порту, сверить `401` без ключа,
   `200` с ключом, старые числа аптек/строк и даты, пагинацию/`409`, `503` для
   pending. После этого остановить старый контейнер и запустить новый на
   `127.0.0.1:18080`; проверить путь через `.81` и основной URL через `.80`.
   Не менять DNS всего сайта.
6. Сохранить старый образ и согласованную SQLite-копию для отката. Откат
   приложения возвращает старую версию **с выключенным центральным сбором**;
   снимки, поступившие только в PostgreSQL после переключения, назад в SQLite
   автоматически не экспортируются.

Нельзя удалять SQLite-копию, том PostgreSQL и старый образ до подтверждённого
восстановления резервной копии и завершения окна отката. Отдельный сборщик
кассы подключается позже, после проверки живой локальной БД и её прав `SELECT`.
Ключ кассы и путь загрузки не совпадают с Bearer-ключом и путём чтения.

### Исполнимая схема параллельной проверки на `.81`

Из `stock-service/` сохраните прежний Compose как `compose.rollback.yml` **до**
переключения Git-ветки и прежний образ под отдельным тегом. Для одноразового
импорта используйте согласованную копию по пути
`/home/adm-quasar/stock-pg-import/stocks.sqlite`, а не работающий файл SQLite.
После подготовки `.env` и отдельного смонтированного тома команды таковы:

```bash
sudo docker compose config --quiet
sudo docker compose --profile migration build stock stock-db-init stock-migrate
sudo docker compose up -d postgres
sudo docker compose run --rm stock-db-init
sudo env STOCK_HOST_DATA_DIR=/home/adm-quasar/stock-pg-import \
  docker compose --profile migration run --rm --user "$(id -u):$(id -g)" stock-migrate
sudo docker run --rm -d --name epharm-stock-candidate \
  --network stock-service_default --env-file .env \
  -e STOCK_PG_HOST=postgres -p 127.0.0.1:18081:8080 \
  epharm-stock-service:local
curl -fsS http://127.0.0.1:18081/readyz
```

Для проверки с Bearer возьмите ключ из защищённого хранилища администратора;
не помещайте его в команду, которую сохранит shell history. Сверьте ответы
кандидата на `18081` с сохранёнными ответами старого API. После успешной
проверки переключите контейнеры:

```bash
sudo docker stop epharm-stock-candidate
sudo docker compose stop stock
sudo docker compose up -d --no-build stock
curl -fsS http://127.0.0.1:18080/readyz
sudo docker compose ps
```

`stock-service_default` — имя сети при запуске Compose из этого каталога без
переопределённого project name; перед командой `docker run` проверьте его
командой `sudo docker network ls`. Если новая версия не проходит проверки,
остановите её, восстановите тег прежнего образа и выполните
`sudo docker compose -f compose.rollback.yml up -d --no-build stock` с прежним
`.env` и неизменным `STOCK_COLLECTION_ENABLED=false`. PostgreSQL и его дамп
сохраните для расследования; старый контейнер читает только SQLite.
