# Остатки Standard-N

## Назначение

`stock-service/` — отдельный .NET 10 сервис на сервере магазина. Он читает общую базу
Standard-N через Firebird 2.5 учётной записью только для чтения, хранит снимки в
собственном SQLite и отдаёт данные через версионированный API. POSM уже использует
тот же провайдер Firebird, кодировку `WIN1251` и подход к ограниченным запросам;
рабочий поток кассы не меняется.

В проверенной схеме источник аптек — `VW_G$PROFILES` (ID, CAPTION, SCITY, ADRESS,
APTEKA_NUMBER), источник партий остатков — `WAREBASE_G` (PART_ID, G$PROFILE_ID,
SNAME, BCODE_IZG, BARCODE, QUANT, PRICE, GODENDO, SERIA, EDIZM). Сервис выбирает
профили с APTEKA_NUMBER и строки с QUANT > 0. Партии не объединяются: срок годности,
серия и цена относятся к конкретной строке. Нет динамического SQL к Firebird.
Каждый SELECT выполняется в транзакции `Read | ReadCommitted | RecVersion | NoWait`
с таймаутом и немедленным rollback после чтения.

ID профиля Standard-N — ключ этого API. ID в реестре HQ/Medusa имеет другой формат;
автоматического сопоставления между ними нет. Потребителям нужно хранить явную
таблицу соответствий, если нужен общий идентификатор с HQ. Число и названия аптек
на странице отражают профили Standard-N, включая профили, помеченные в имени как
закрытые; сервис не угадывает статус по названию или неоднозначному STATUS.

## Обновление и нагрузка

Первый запрос остатков аптеки получает полный снимок из Standard-N. Повторный запрос
в течение 180 секунд читает локальный снимок. Фоновый работник обновляет запрошенные
за последние 24 часа аптеки после истечения TTL. Одновременно выполняется максимум
один запрос к Firebird. При ошибке старый снимок сохраняется и помечается `error`;
повторная попытка после двухминутной паузы. API показывает `asOf`, `snapshotId` и
`status` (`fresh`, `stale`, `error`, `pending`). Если первый снимок недоступен, ответ
`503` без подмены данных нулём.

Это ограничение нагрузки намеренно: 5 октября 2026 года в источнике было 586 профилей,
а одна проверенная аптека дала 4 916 положительных строк примерно за 1,6 секунды
узкого чтения. Полный обход всех профилей каждые три минуты потребовал бы гораздо
большей параллельной нагрузки на рабочую базу. Для строгого трёхминутного SLA по всей
сети нужна отдельная нагрузочная проверка с владельцем Standard-N и, вероятно,
поток изменений или распределённый сбор POSM. Текущий контракт гарантирует
трёхминутный TTL и обновление активно запрашиваемых аптек при доступности источника;
при задержке статус и время снимка остаются видимыми.

## Публичная страница и API

Публичный HTTPS-маршрут `/stocks/` открывает страницу после HTTP Basic авторизации.
Разделы: города с количеством профилей → аптеки города → партии остатков. На странице
аптеки доступны поиск по наименованию/штрихкоду, пагинация и выгрузка всех строк
текущего снимка в XLSX. Excel содержит время снимка; количества и цены записаны
числами, названия/штрихкоды — текстом.

Для других модулей и будущего DWH используется Bearer-ключ. Basic и Bearer работают
на том же API, но значения ключей разные. API доступен только через HTTPS-прокси,
а контейнер сервиса не публикует собственный порт наружу.

| Запрос | Назначение |
| --- | --- |
| `GET /stocks/api/v1/cities` | Города и число профилей. |
| `GET /stocks/api/v1/pharmacies?city=...` | Аптеки города, ID, статус, число строк, время снимка. |
| `GET /stocks/api/v1/pharmacies/{id}` | Метаданные одной аптеки. |
| `GET /stocks/api/v1/pharmacies/{id}/stocks?limit=100&offset=0&q=...` | Страницы партий; `limit` 1–500. |
| `GET /stocks/api/v1/pharmacies/{id}/stocks.xlsx` | Все строки одного снимка в XLSX. |

Первая страница JSON возвращает `snapshotId` и `asOf`. Для следующих страниц
интеграция передаёт `snapshot=<snapshotId>`: если снимок сменился, API отвечает `409
snapshot_changed`, и клиент начинает чтение заново. Это предотвращает тихие пропуски
при пагинации во время обновления.

Пример запроса интеграции без настоящего ключа:

```bash
curl -H 'Authorization: Bearer <api-key>' \
  'https://inkeshopapteka.inkar.kz/stocks/api/v1/pharmacies/1/stocks?limit=100&offset=0'
```

## Развёртывание и откат

Каталог сервиса на сервере: `/home/adm-quasar/stock-service`. Его `compose.yml`
подключает контейнер к сети `inkar-shop_frontend` для Caddy. Перед запуском создать
`data/` с владельцем UID/GID 1654 и `.env` с правами `0600` по `.env.example`.
В `.env` задаются источник Firebird, пароль read-only учётной записи, отдельные
случайные пароль страницы и Bearer-ключ. Файл и снимки SQLite не коммитятся.

Маршрут Caddy на публичном HTTPS-сайте:

```caddyfile
redir /stocks /stocks/ 308
handle_path /stocks/* {
    reverse_proxy epharm-stock-service:8080
}
handle {
    reverse_proxy router:8080
}
```

В рабочем Caddyfile сохраняются существующие заголовки и параметры fallback-прокси.
Сначала собрать/запустить новый контейнер, проверить его `/healthz` из сети Caddy,
затем проверить изменённый Caddyfile командой `caddy validate` и применить его.
После публикации проверить `401` без авторизации, вход через HTTPS, города, одну аптеку,
поиск, Excel, Bearer API и статус снимка. При проблеме маршрута вернуть резервную
копию Caddyfile и перезапустить Caddy; контейнер сервиса можно остановить отдельно.
На текущем сервере Caddy запущен с `admin off`, поэтому после изменения файла нужен
`docker restart inkar-shop-edge-1` вместо `caddy reload`. Конфигурация магазина
смонтирована из каталога текущего релиза: при следующем релизе магазина маршрут
`/stocks/` нужно перенести в новый Caddyfile перед переключением релиза. Резервная
копия исходного Caddyfile оставляется рядом с изменённым файлом.
Пароль страницы и Bearer-ключ хранятся только в `.env` на сервере; их может получить
администратор с SSH-доступом к `/home/adm-quasar/stock-service/.env`.
SQLite хранит снимки между рестартами. Для резервного копирования использовать
согласованный SQLite backup или остановить контейнер и сохранить `data/`; не копировать
только основной файл в режиме WAL во время записи.

## Проверки

```bash
dotnet test stock-service-tests/stock-service-tests.csproj
dotnet publish stock-service/StockService.csproj -c Release
node --check stock-service/wwwroot/app.js
```

Тесты проверяют атомарность смены снимка, буквальный поиск по `%` и типы ячеек XLSX.
Рабочую базу нельзя использовать для нагрузочного теста без отдельного окна и наблюдения
за её состоянием. Настройки таймаута/TTL находятся в `.env.example`.
