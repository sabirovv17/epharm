# Интеграция рекомендаций и товарных остатков мерчендайзинга

## Что является источником истины

- ePharm сохраняет свой каталог, локальные правила, чеки, атрибуцию продажи и денежный баланс фармацевта.
- CRM мерчендайзинга добавляет только аптечно-зависимые рекомендации и снимок товарного остатка.
- Рекомендация CRM превращается в обычное `recommendation_event` ePharm. Принятие, фактическая продажа и бонус проходят через существующий идемпотентный контур ePharm; отдельного денежного баланса не создаётся.
- Пустое поле остатка означает «источник не сообщил значение». Оно никогда не преобразуется в ноль.

## Поток данных

1. POSM передаёт ePharm текущую корзину.
2. ePharm рассчитывает свои активные правила.
3. Backend ePharm запрашивает у CRM `/api/integrations/pharmapay/recommendations/context`. В запросе есть только `pharmacyId`, точные идентификаторы товаров корзины и товары локальных рекомендаций. ФИО/ID фармацевта и `sessionId` наружу не передаются.
4. CRM находит аптеку через `epharm_branch_crosswalk`, возвращает активные рекомендации и свежие снимки остатка.
5. ePharm повторно проверяет точный триггер и однозначно разрешает рекомендуемый товар в своём каталоге. Неизвестный или неоднозначный EAN/iPartID отбрасывается.
6. Сначала остаются канонические локальные правила ePharm; CRM заполняет свободные места в лимите 5 замен + 5 допродаж. Дубликаты товара удаляются.
7. Окно кассы показывает остаток в аптеке, по сети и на складе вместе со временем снимка. Просроченный снимок помечается как устаревший.

Сбой CRM, таймаут, неверный payload или исчерпание bulkhead не блокируют кассу: ePharm продолжает отвечать локальными рекомендациями.
Ответ с `available=false` или `pharmacyMapped=false` игнорируется целиком, даже если содержит списки.
Все переданные идентификаторы рекомендуемого товара должны однозначно указывать на один товар;
можно передавать одновременно productId, EAN и iPartID, но противоречивые или неизвестные ключи не допускаются.

Один и тот же конкретный триггер и предлагаемый товар не могут одновременно выступать заменой и
допродажей. При таком конфликте между источниками сохраняется локальное правило ePharm, а
противоречащее предложение CRM отбрасывается. Если оба противоречащих предложения пришли из CRM,
не показываются оба; причина возвращается в `conflicts`. Разные триггеры не смешиваются.

Нулевой остаток может скрыть предложение только при `status=confirmed` и `observedAt` не старше
30 минут и не позже текущего серверного времени. Этот предел соответствует документированному
`PHARMAPAY_BALANCE_MAX_AGE_SECONDS=1800` на CRM. Старый или будущий подтверждённый снимок
помечается `stale`, снимок без времени — `unknown`; они не скрывают локальные рекомендации.

## Контракт CRM

`POST /api/integrations/pharmapay/recommendations/context`

Заголовок: `X-Pharmapay-Key: <общий серверный секрет>`.

Пример запроса:

```json
{
  "pharmacyId": "ph_t",
  "cart": [{"sku": "80309", "barcode": "4603423004936", "name": "Bioderma", "qty": 1}],
  "requestedProducts": [{"productId": "p_zen", "barcode": "4870000000013"}]
}
```

Пример ответа:

```json
{
  "available": true,
  "pharmacyMapped": true,
  "generatedAt": "2026-10-19T10:30:00Z",
  "recommendations": [{
    "id": "8ffafcf4-f0a0-4662-bcd2-1dd3c11bd888",
    "kind": "crosssell",
```

## Подготовка CRM

1. Применить миграцию `067_pharmapay_recommendations_and_balances.sql`.
2. Проверить, что каждая аптека имеет однозначную строку в `epharm_branch_crosswalk`.
3. Подготовить JSON для `scripts/sync_pharmapay_context.py`. Поля рекомендации должны быть согласованы медицинским/коммерческим владельцем; планограмма сама по себе рекомендацию не создаёт.
4. Выполнить безопасный dry-run:

```bash
python scripts/sync_pharmapay_context.py /secure/import/context.json
```

5. После проверки счётчиков применить тот же файл:

```bash
python scripts/sync_pharmapay_context.py /secure/import/context.json --apply --confirm-pharmacy-count 1
```

6. На CRM задать `PHARMAPAY_INTEGRATION_KEY` и `PHARMAPAY_BALANCE_MAX_AGE_SECONDS=1800`. Ключ должен совпадать с ePharm и не попадать в браузер.

## Включение ePharm

```dotenv
MERCH_TASKS_ENABLED=true
MERCH_TASKS_BASE_URL=http://10.10.1.80:8080
MERCH_TASKS_INTEGRATION_KEY=<тот же длинный случайный ключ>
MERCH_RECOMMENDATIONS_TIMEOUT_MS=900
```

Plain HTTP допускается клиентом только для loopback/RFC1918-адреса. Для публичного адреса обязателен HTTPS. Редиректы запрещены, чтобы секретный заголовок не ушёл на другой host.

## Приёмка перед полным включением

- Запрос неизвестной аптеки возвращает `pharmacyMapped=false`, пустые списки и не ломает POSM.
- Известный EAN вызывает ровно ожидаемую рекомендацию; name-only совпадение CRM не использует.
- Неоднозначный EAN/iPartID рекомендуемого товара в каталоге ePharm не показывается.
- При `networkAvailableQty=null` интерфейс не показывает сеть как `0`.
- Снимок старше лимита виден как «Остаток устарел» с временем.
- Отключённая CRM/HTTP 503/таймаут не меняют результат локальных правил ePharm.
- `available=false`/`pharmacyMapped=false` с непустыми списками также не меняют локальные правила.
- Два/три согласованных идентификатора одного товара не вызывают ошибку; несовпадающие ключи отклоняются.
- Нулевой остаток без времени, старше 30 минут или с будущим временем не скрывает предложение.
- Противоречия замена/допродажа одной пары подавляются без потери канонического локального правила.
- CRM не вытесняет локальные предложения и не превышает общий лимит 5 замен + 5 допродаж.
- Принятая CRM-рекомендация создаёт один `pending_bonus`; повтор запроса/ACK не удваивает начисление.
- Фактический чек закрывает событие существующим механизмом продажи, а выплата отражается в общем балансе ePharm.

## Откат

Установить `MERCH_TASKS_ENABLED=false` и перезапустить только backend ePharm. Локальные рекомендации, продажи и баланс продолжат работать. Таблицы CRM можно оставить для расследования; их удаление для отката не требуется.
