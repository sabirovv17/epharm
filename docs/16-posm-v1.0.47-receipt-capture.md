# POSM v1.0.47: безопасный захват состава чека

## Цель

Версия 1.0.47 добавляет доказательную копию состава продажи и устойчивую связь:

`аптека -> документ Standard-N -> позиции iPartID/EAN -> внутренние productId Epharm`.

Решение намеренно не вмешивается в оплату и фискальную печать. POSM только читает уже доступные
данные Standard-N, хранит собственные файлы в `C:\Epharm` и отправляет структурированную продажу в
существующий backend.

## Жизненный цикл

1. При открытом чеке POSM читает `DOCS`/`DOC_DETAIL_ACTIVE` и события `zkassa.log`.
2. После каждого изменения небольшая JSON-копия атомарно заменяется в
   `C:\Epharm\receipts\active\<saleId>\sale.json`.
3. Завершение подтверждается одним из независимых сигналов:
   - документ исчез из активного Firebird-чека;
   - Standard-N записал маркер завершения очереди печати;
   - Standard-N переключился на следующий документ.
4. POSM формирует immutable `pending\<saleId>\sale.json` и `receipt.png`, затем ставит ту же продажу
   в SQLite outbox.
5. При отсутствии интернета outbox и pending остаются на диске. После перезапуска они повторно
   обнаруживаются и отправляются с тем же id.
6. После HTTP 2xx backend ACK POSM удаляет только собственную папку `pending\<saleId>`.

## Идентификаторы и база

- `pharmacyId` берётся из установленного аптечного `posm.json` и не меняется автообновлением.
- `sourceDocumentId` — локальный `DOCS.ID` Standard-N; это не фискальный номер.
- `saleId` детерминирован по `pharmacyId + sourceDocumentId`, поэтому повторная отправка безопасна.
- Каждая позиция сохраняет исходные `iPartID`, EAN, имя, цену и количество.
- Backend выполняет тот же строгий barcode/iPartID/name matching, что Rules Engine, и добавляет
  внутренний `productId`. Неоднозначный результат остаётся `null`, произвольный товар не выбирается.

Миграция V041 добавляет к `pos_sales` источник завершения, локальный id документа и формат
артефакта. Внутренний `productId` хранится в JSON каждой позиции рядом с исходными данными.

## Файлы

| Каталог      | Назначение                                      | Удаление                                   |
| ------------ | ----------------------------------------------- | ------------------------------------------ |
| `active`     | Атомарный черновик открытой корзины             | при отмене, завершении или после retention |
| `pending`    | Завершённые JSON + PNG до подтверждения сервера | только после backend ACK                   |
| `quarantine` | Повреждённые файлы для диагностики              | вручную после расследования                |

PNG содержит наблюдаемый состав, аптеку, Standard-N document id, время, продавца и сумму. На нём
явно написано, что это не фискальный чек.

## Fail-safe свойства

- нет записи в Firebird;
- нет удаления или изменения `zkassa.log`;
- нет перехвата/задержки Windows Print Spooler;
- нет замены драйвера ККМ;
- ошибка PNG не блокирует кассу и структурированную sale-очередь;
- ошибка сети не удаляет pending;
- повторные сигналы завершения не создают дубликаты;
- повреждённый pending изолируется, а не удаляется молча.

## Что пока не является реализованным

Это не точная копия официального фискального документа. В активной корзине нет достоверных полей
QR/OFD, способа оплаты, номера ФН, ФПД и результата печати ККМ. Их нельзя придумывать или извлекать
записью в кассовую систему. Для официального PDF/PNG необходимо отдельно подтвердить один из
read-only источников на боевой конфигурации: API драйвера ККМ, OFD API или RAW spool capture.

При аварийном отключении Windows после физической печати, но до обоих наблюдаемых сигналов
завершения, остаётся active-черновик. Он намеренно не превращается в продажу автоматически: иначе
отменённая корзина могла бы дать ложную продажу и бонус.

## Пилотная приёмка

Перед массовым релизом проверить на одной аптеке:

1. обычную продажу из 1 и нескольких позиций;
2. удаление позиции и полную отмену чека;
3. наличную/безналичную оплату без изменения поведения Standard-N;
4. два быстрых последовательных чека без смешивания составов;
5. отключение интернета до оплаты и доставку после восстановления;
6. перезапуск POSM/Windows с pending на диске;
7. отсутствие дублей по одному `DOCS.ID`;
8. наличие `productId` у однозначно сопоставленных товаров и `null` у неоднозначных;
9. удаление pending только после появления продажи на backend;
10. отсутствие дополнительной задержки интерфейса и фискальной печати.

Откат локального PNG без отключения sale reporting:

```powershell
setx EPHARM_RECEIPT_CAPTURE_ENABLED false
```

После изменения переменной требуется перезапуск POSM. Для возврата удалить переменную или задать
`true`.
