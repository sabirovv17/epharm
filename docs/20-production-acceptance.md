# P1 Production Acceptance

Этот runbook — исполняемый чек-лист для оставшихся P1. Он не заменяет фактическую
проверку на production и реальной кассе: каждый пункт закрывается только ссылкой на
лог/скриншот/ID объекта, временем, исполнителем и результатом rollback-проверки.

## Общие правила

- Зафиксировать release commit, backup ID, окно работ, ответственного и rollback owner.
- Запускать `tools/check-p0-config.sh`, полные CI checks и smoke из `docs/RELEASE-CHECKLIST.md`.
- Не менять production-данные прямым SQL, кроме согласованного аварийного runbook.
- Не переносить секреты, телефоны, ФИО и содержимое чеков в issue/чат/репозиторий.
- Любой fail-closed отказ считается успешной проверкой только если оператор видит понятное
  состояние и заказ/бонус не проходит дальше.

## 1. Обучение и RBAC

Предусловия: один тестовый фармацевт `pending`, отдельная тестовая программа и по одному
администратору каждой роли. Работать через production UI/API под соответствующей ролью.

1. Активировать тестового фармацевта и подтвердить вход реальным OTP.
2. Создать программу, этапы (контент + тест), награду и назначение именно этому профилю.
3. В мобильном приложении пройти маршрут, проверить блокировку следующего этапа, тест,
   повтор неуспешной попытки, успешное завершение, однократную награду и сертификат.
4. Назначить программу повторно. Подтвердить отсутствие повторного начисления за прежнее
   событие и корректный новый lifecycle.
5. Для каждой роли — `SYSTEM_ADMIN`, `HQ_HEAD`, `TRAINING_MANAGER`, `REGIONAL_MANAGER`, `TRAINER`,
   `CATEGORY_LEAD`, `BRAND_MANAGER`, `FINANCE_REVIEWER` — выполнить разрешённые read/write действия
   и попытаться выполнить запрещённые. Ожидание: UI скрывает действие, API независимо возвращает 403.
6. Удалить/архивировать только созданные тестовые объекты согласно продуктовой политике.

Артефакты: ID фармацевта/программы/назначений, timestamps событий, ledger entry, certificate ID,
матрица роль × endpoint с HTTP-кодами. Никаких реальных персональных данных.

## 2. Standard-N seller mapping

Код поддерживает явное правило `(pharmacyId, external USER_ID) -> active pharmacist` и применяет
его раньше эвристик имени. В админке: **Фармацевты → Standard-N mapping**.

1. Убедиться, что нужный профиль активен и прикреплён к той же аптеке.
2. В списке несопоставленных продавцов выбрать внешний `USER_ID` (например `33`) и профиль.
3. Провести тестовую продажу и проверить источник `standardn_explicit_mapping`, pharmacist ID,
   рекомендацию и отсутствие повторного бонуса при retry того же `saleId`.
4. Отозвать правило, повторить безопасный тест и убедиться, что продажа остаётся видимой, но
   не привязывается к человеку. Затем восстановить правило.

Артефакты: mapping ID, pharmacy ID, внешний USER_ID, sale ID, источник сопоставления и audit ID.

## 3. POSM на реальной кассе

Предусловия: индивидуальный токен выдан в **Исполнение → Кассы**, legacy enrollment выключен,
конфигурация привязана к одной аптеке, установлены watchdog/autostart и pinned update public key.

1. Recommendation: добавить триггерный товар, увидеть рекомендацию; удалить триггер и убедиться,
   что popup исчез и outcome не превращается в продажу.
2. Customer display: проверить состав чека и 12 роликов, порядок, cache и возврат эфира.
3. Offline: отключить сеть, создать shown/outcome/sale; вернуть сеть и доказать ровно одну доставку.
4. Receipt capture: наблюдать `active -> pending -> backend ACK -> delete`; при network fault
   `pending` должен сохраниться, при reboot — восстановиться без дубля.
5. Перезагрузить Windows/приложение, проверить watchdog, presence и heartbeat этой кассы.
6. Отозвать токен в админке: все POSM API должны дать 401; новый токен работает только для
   своей пары device/pharmacy.
7. Обновление: валидно подписанный пакет ставится; изменение URL, SHA или signature отклоняется.

Фискальный artifact принимается только от согласованного producer с точным PDF/PNG, manifest и
SHA-256. До установки официального hardware-specific producer состояние `waiting` корректно.
Авария после физической печати не закрывается догадкой: нужен подтверждённый closed-receipt source.

## 4. Fulfillment pilot: одна аптека, две кассы

Предусловия: стабильный storefront pharmacy ID связан с внутренней аптекой; обе кассы имеют
индивидуальные токены; `FULFILLMENT_ENABLED=false` до финального Go; зафиксирован UTC
`EPHARM_ORDER_START_AT`; доверенные payment authorities пусты до подключения webhook producer.

1. Включить backend и worker только на пилотной аптеке/границе времени.
2. Один заказ доставить повторно тем же event/body: второй ACK должен быть идемпотентным.
   Повторить event/order ID с другим body: ожидать conflict и отсутствие второго заказа.
3. Отключить сеть первой кассы, принять/обновить заказ со второй; после reconnect первая должна
   догнать монотонный feed без отката статуса.
4. Проверить неверный и верный код, lockout, optimistic version conflict и повтор выдачи.
5. Проверить наличные с явным подтверждением, отмену и обновление кабинета покупателя.
6. Карточный `paid` от браузера/неразрешённого источника должен храниться как `pending`, а кнопка
   выдачи — блокироваться. Только согласованный server-to-server producer можно добавить в
   `FULFILLMENT_TRUSTED_CARD_PAYMENT_AUTHORITIES`.
7. Частичную выдачу не включать в пилот без утверждённой модели перерасчёта, возврата оплаты и
   строкового статуса. Текущий контракт намеренно поддерживает только атомарную выдачу заказа.
8. Go/No-Go: оставить одну аптеку, собрать метрики минимум одну смену; при ошибке выключить worker,
   затем backend flag, не удаляя outbox и audit.

## 5. Внешние решения, которые код не может принять сам

| Решение             | Минимальное доказательство до Go                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Карточная оплата    | Документированный webhook/API эквайера, проверка подписи, payment/order binding, replay protection, refund/cancel semantics и owner |
| Фискальный producer | Модель и версия ККМ/драйвера, read-only API, ACL inbox, точный artifact, закрытый чек и тест после авар/reboot                      |
| Частичная выдача    | Политика суммы/остатка/возврата, модель line quantities, состояние кабинета и фискальная коррекция                                  |
| Массовый enrollment | Список предварительно одобренных device IDs/pharmacy IDs, owner ротации, SLA отзыва и аудит выдачи                                  |
